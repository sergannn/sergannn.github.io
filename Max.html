Как я отправил музыку в MAX как аудиосообщение

Подробный учебный разбор: от неудачных попыток через интерфейс до чтения обфусцированного кода MAX Web, поиска авторизации в локальной базе Chrome и отправки аудио через внутренний механизм MAX.

Практический пример: канал MAX “Джаз есть везде”, файл MP4 с музыкой, цель — получить inline-аудио на 03:13, а не обычный файл.

1. Что надо было сделать

Была задача отправить музыку из MP4 в публичный канал MAX не как файл, а как аудиосообщение, которое сразу проигрывается в ленте. То есть нужен не блок “Скачать файл”, а аудио-плашка с длительностью, например 03:13.

Исходный файл лежал локально:

/Users/servas/Downloads/_Подмосковные вечера - BENKO DIXIELAND BAND.mp4

Публичный канал:

https://max.ru/channel_piano_clarinet
https://web.max.ru/-79157065918537

Важно. Эта инструкция объясняет исследовательский путь и локальную автоматизацию под своим аккаунтом. Не надо использовать чужие токены, чужие профили Chrome или отправлять сообщения без разрешения владельца аккаунта.

2. Словарь простыми словами

Перед техническими шагами полезно договориться о словах. Ниже не академические определения, а рабочие объяснения: что это значит именно в задаче с MAX Web.

Браузерное веб-приложение Это сайт, который ведет себя как приложение. MAX Web открывается как страница, но внутри страницы загружается много JavaScript-кода, который сам рисует интерфейс, держит соединение с сервером и отправляет сообщения.
JavaScript Язык, на котором работает логика сайта в браузере. Когда нажимаешь кнопку “Отправить”, обычно выполняется JavaScript-функция.
Бандл Большой JavaScript-файл, собранный из многих маленьких файлов проекта. Разработчики пишут сотни модулей, а сборщик упаковывает их в файлы вроде CHBUOM21.js.
DevTools Инструменты разработчика в Chrome. Открываются через Cmd + Option + I на macOS или через меню “View → Developer → Developer Tools”. Там видно сеть, код, ошибки, хранилища сайта и консоль.
Console Вкладка DevTools, где видны ошибки сайта и где можно выполнять JavaScript вручную. Именно там можно заметить серверную ошибку вроде errors.process.attachment.video.not.ready.
Network Вкладка DevTools, где видно, какие файлы и запросы делает сайт: HTML, JavaScript, картинки, WebSocket-соединения, загрузки файлов.
Sources Вкладка DevTools, где можно читать загруженный JavaScript. В production-коде он часто сжат и сложен, но по строкам и константам все равно можно найти нужные места.
Application Вкладка DevTools, где видно хранилища сайта: Local Storage, IndexedDB, cookies, Cache Storage. Для MAX там были ключи авторизации и локальные кэши.
Local Storage Простое хранилище “ключ → значение” внутри браузера для конкретного сайта. MAX Web хранит там служебные ключи, включая авторизационные данные. Их нельзя публиковать.
IndexedDB Более сложная локальная база данных внутри браузера. Сайт может хранить там кэш чатов, сообщений, пользователей и другой структурированный мусор/данные, чтобы быстрее открываться.
LevelDB Формат локальной базы, в котором Chrome физически хранит Local Storage и IndexedDB на диске. Поэтому мы читали папку Chrome через библиотеку classic-level.
WebSocket Постоянное соединение между браузером и сервером. В мессенджерах оно часто используется для отправки/получения сообщений без перезагрузки страницы.
Attach / вложение Объект, который описывает файл, аудио, видео или картинку внутри сообщения. Для MAX было принципиально получить attach типа AUDIO, а не обычный attach файла.
Token Секретная строка, доказывающая серверу, что это именно твоя авторизованная сессия. Токен нельзя показывать в HTML, логах, скриншотах и GitHub.
Playwright Библиотека для программного управления браузером. Здесь она нужна не для “клика мышкой”, а чтобы открыть временный Chrome-профиль, положить туда авторизацию и выполнить код внутри страницы.
ffmpeg Утилита для работы с аудио и видео. Ей я вытащил аудиодорожку из MP4 и сделал M4A.

3. Что сначала не сработало

Загрузка M4A как файла

Первый очевидный путь — вытащить аудио из MP4 и загрузить его в MAX как файл. Я сделал M4A:

ffmpeg -hide_banner \
  -i "/Users/servas/Downloads/_Подмосковные вечера - BENKO DIXIELAND BAND.mp4" \
  -vn -c:a aac -b:a 128k -movflags +faststart \
  "/Users/servas/Downloads/_Подмосковные вечера - BENKO DIXIELAND BAND.m4a" \
  -y

Разберем команду по кускам:

Фрагмент Что означает
ffmpeg Запускает программу ffmpeg. Это универсальная утилита для конвертации аудио и видео.
-hide_banner Убирает длинную служебную “шапку” ffmpeg из вывода. На результат не влияет, просто делает консоль чище.
-i "...mp4" -i означает input, то есть входной файл. Здесь мы говорим ffmpeg: возьми исходный MP4 с музыкой.
-vn Video none: не брать видеодорожку. Нам нужно только аудио, поэтому картинку из MP4 выбрасываем.
-c:a aac Codec audio: закодировать аудио кодеком AAC. AAC хорошо подходит для файла .m4a и обычно нормально воспринимается веб-приложениями.
-b:a 128k Bitrate audio: качество/поток аудио 128 килобит в секунду. Для голосового/музыкального сообщения это разумный компромисс между размером и качеством.
-movflags +faststart Переносит служебные метаданные MP4/M4A в начало файла. Тогда файл быстрее начинает проигрываться при потоковой загрузке, потому что плееру не надо ждать конец файла.
"...m4a" Выходной файл. Расширение .m4a означает аудио-контейнер MPEG-4 без видео.
-y Разрешает перезаписать выходной файл без вопроса “Overwrite?”. Удобно для повторных запусков.
\ Обратный слэш в конце строки в macOS/Linux означает: команда продолжается на следующей строке. Это только оформление, чтобы длинная команда читалась легче.

Итог простыми словами: “Возьми MP4, выброси видео, аудио перекодируй в AAC 128k, сохрани как M4A и подготовь файл к быстрому старту воспроизведения”.

Но если прикрепить этот M4A через обычную кнопку загрузки файла, MAX показывает его как файл-вложение. Это не подходит, потому что пользователю приходится открывать или скачивать файл.

Фейковый микрофон Chrome

Потом был вариант запустить Chrome с fake microphone и подставить аудио вместо микрофона:

open -na "Google Chrome" --args \
  --use-fake-device-for-media-stream \
  --use-fake-ui-for-media-stream \
  --use-file-for-fake-audio-capture="/Users/servas/Downloads/_Подмосковные вечера - BENKO DIXIELAND BAND.fake-mic.wav" \
  "https://web.max.ru/-79157065918537"

Перед этим WAV был сделан так:

ffmpeg -hide_banner -y \
  -i "/Users/servas/Downloads/_Подмосковные вечера - BENKO DIXIELAND BAND.mp4" \
  -vn -ac 1 -ar 48000 -sample_fmt s16 \
  "/Users/servas/Downloads/_Подмосковные вечера - BENKO DIXIELAND BAND.fake-mic.wav"

Технически это могло бы работать, но способ плохой: нужно нажимать или удерживать кнопку записи. Это именно тот “ручной костыль”, которого хотелось избежать.

Попытка через javascript: в адресной строке

Еще один неудачный путь — выполнить небольшой JavaScript прямо в открытой странице браузера. В теории это удобно: вставляешь код в адресную строку или Console, и он выполняется внутри MAX Web.

На практике случилась типичная ошибка: фокус был не в адресной строке, а в поле ввода сообщения MAX. Поэтому текст javascript:... не выполнился как код, а отправился как обычное сообщение в канал.

Вывод: для повторяемой автоматизации нельзя полагаться на ручной фокус браузера. Надежнее использовать отдельный временный профиль и выполнять код через Playwright внутри страницы.

Смысл того одноразового скрипта был такой: прямо из открытой страницы MAX найти JS-бандл, импортировать его как модуль, найти текущий чат и вызвать внутреннюю функцию отправки аудио. Полная реальная версия включала бы огромную строку audioBase64 с содержимым аудиофайла, поэтому ниже показана та же структура без самого большого бинарного куска:

javascript:(async () => {
  // 1. Найти JS-бандл MAX, где лежат внутренние функции приложения.
  const bundleUrl = [...document.scripts]
    .map((script) => script.src)
    .find((src) => /CHBUOM21\.js/.test(src))
    || performance.getEntriesByType("resource")
      .map((entry) => entry.name)
      .find((src) => /CHBUOM21\.js/.test(src));

  if (!bundleUrl) {
    throw new Error("MAX bundle was not found");
  }

  // 2. Импортировать этот бандл как ES module.
  const mod = await import(bundleUrl);

  // 3. Взять id чата из URL:
  // https://web.max.ru/-79157065918537 => -79157065918537
  const targetId = location.pathname.slice(1);

  // 4. Найти объект чата во внутреннем кэше MAX.
  const chat = Array.from(mod.Co.chats.cache.values()).find((item) => {
    if (!item || item instanceof Error) return false;
    const id = item.id?.toString?.() ?? String(item.id ?? "");
    return id === targetId;
  });

  if (!chat) {
    throw new Error("chat not found");
  }

  // 5. Здесь должна была быть длинная base64-строка аудио.
  // В HTML ее публиковать бессмысленно: она огромная.
  const audioBase64 = "AAAA...ЗДЕСЬ_БЫЛО_СОДЕРЖИМОЕ_AUDIO...";

  // 6. Превратить base64 обратно в байты.
  const bytes = Uint8Array.from(
    atob(audioBase64),
    (char) => char.charCodeAt(0)
  );

  // 7. Создать браузерный File, как будто пользователь выбрал файл.
  const file = new File(
    [bytes],
    "_Подмосковные вечера - BENKO DIXIELAND BAND.m4a",
    { type: "audio/mp4" }
  );

  // 8. Сделать простую волну для визуального отображения аудиосообщения.
  const wave = new Uint8Array(
    Array.from({ length: 80 }, (_, i) => {
      return 28 + Math.round(20 * Math.abs(Math.sin(i / 5)));
    })
  );

  // 9. Вызвать внутреннюю функцию MAX для отправки аудио.
  await mod.ja({
    chat,
    file,
    duration: 193369,
    wave
  });
})()

Разбор этого скрипта по шагам:

Строка Зачем нужна
javascript:(async () => { ... })() Bookmarklet-форма: если вставить это именно в адресную строку, браузер выполнит код на текущей странице. async нужен, чтобы использовать await.
document.scripts Список всех <script>, которые подключены к странице. Так можно найти URL бандла MAX.
performance.getEntriesByType("resource") Запасной способ найти загруженные ресурсы страницы, если нужного URL нет в document.scripts.
/CHBUOM21\.js/.test(...) Проверка имени файла. В тот момент нужная логика MAX была именно в бандле CHBUOM21.js.
await import(bundleUrl) Загружает JS-бандл как модуль и возвращает объект экспортов. После этого можно обратиться к mod.Co, mod.ja и другим экспортированным частям.
location.pathname.slice(1) Берет id текущего канала из адреса страницы. Убираем первый символ /.
mod.Co.chats.cache.values() Внутренний кэш чатов MAX Web. В нем искался объект текущего канала.
atob(audioBase64) Декодирует base64 обратно в бинарные данные. Base64 — это способ представить файл текстовой строкой.
new File(...) Создает объект файла прямо в браузере. Для MAX он выглядит как выбранный пользователем аудиофайл.
duration: 193369 Длительность аудио в миллисекундах. 193369 мс — это примерно 3 минуты 13 секунд.
mod.ja(...) Внутренняя экспортированная функция MAX, которая запускает отправку аудио-вложения.

Почему это отправилось текстом: bookmarklet выполняется только если текст попал в адресную строку браузера. Если в этот момент активным было поле ввода сообщения MAX, браузер ничего не выполняет. Он просто вставляет символы в поле сообщения. Поэтому в канал ушел текст, начинающийся с javascript:(async()=>.

4. Как я пользовался DevTools

DevTools был нужен не для взлома, а для наблюдения: что браузер загружает, какие ошибки появляются, где лежит авторизация, какие JS-файлы отвечают за отправку аудио.

Как открыть DevTools

  1. Открыть https://web.max.ru/-79157065918537 в Chrome.
  2. Нажать Cmd + Option + I.
  3. Если DevTools открылся сбоку, можно перетащить его вниз или в отдельное окно через меню с тремя точками.

Вкладка Console: смотрим ошибки

Console показывает сообщения от JavaScript-кода страницы. Когда первая попытка с .ogg выглядела успешной, именно Console показала, что на самом деле сервер отказался принять сообщение:

[0] cmd errored [0x40 errors.process.attachment.video.not.ready]
Key: errors.process.attachment.video.not.ready

Для новичка важная мысль такая: если интерфейс нарисовал сообщение, это еще не значит, что сервер его принял. Console помогает отличить “локально нарисовано” от “реально отправлено”.

Вкладка Network: смотрим, какие файлы загрузил MAX

Во вкладке Network я включал фильтр JS, обновлял страницу и смотрел JavaScript-файлы. Там видны имена бандлов: CHBUOM21.js, app.C2ONFNRQ.js и другие.

  1. Открыть вкладку Network.
  2. Нажать фильтр JS.
  3. Обновить страницу через Cmd + R.
  4. В списке запросов искать большие JavaScript-файлы.
  5. Открывать файл и смотреть вкладку Headers, чтобы скопировать полный URL.

Так я понял, какие именно бандлы надо выгружать и искать в них строки.

Вкладка Sources: читаем код

Во вкладке Sources можно открыть загруженный JS-файл. Код там сжатый: длинные строки, короткие имена переменных, мало комментариев. Но поиск работает.

Что я делал в Sources:

  1. Открывал CHBUOM21.js.
  2. Нажимал Cmd + F.
  3. Искал строки AUDIO, audioId, MediaRecorder, cmd(64).
  4. Когда находил совпадение, смотрел код вокруг него: какие поля передаются, какие функции вызываются рядом.

Вкладка Application: смотрим хранилища сайта

Application нужна, чтобы увидеть, какие данные MAX хранит в браузере.

  1. Открыть вкладку Application.
  2. Слева найти Storage → Local Storage → https://web.max.ru.
  3. Посмотреть список ключей, начинающихся с __oneme.
  4. Слева также посмотреть IndexedDB, где MAX держит локальные базы.

В DevTools можно увидеть факт наличия ключей. Но для автоматизации удобнее читать эти же данные с диска Chrome, потому что тогда скрипт может сам открыть временный профиль и не просить человека ничего копировать руками.

Как DevTools помог проверить результат

После отправки аудио я не доверял только текущей странице. Я проверял так:

  1. Закрывал временную сессию.
  2. Открывал канал заново.
  3. Смотрел, осталось ли аудио в ленте.
  4. Проверял Console: нет ли ошибки обработки вложения.

Это главный практический урок: для мессенджера важен не DOM в текущей вкладке, а состояние после чистой загрузки с сервера.

5. Как я нашел нужные места в коде MAX Web

MAX Web — это обычное веб-приложение. Браузер загружает JavaScript-бандлы, внутри которых есть весь клиентский код: отправка сообщений, загрузка вложений, работа с WebSocket.

Я шел по простой цепочке вопросов:

  1. Где в коде MAX вообще есть запись голосового сообщения?
  2. Как MAX отличает аудиосообщение от обычного файла?
  3. Какая функция отправляет сообщение на сервер?
  4. Какая функция загружает аудиофайл?
  5. Можно ли вызвать этот путь программно, без удержания кнопки записи?

Я выгрузил JS-бандлы страницы в папку:

/tmp/max-web-bundles

Среди них были файлы вроде:

CHBUOM21.js
6ky1fLXF.js
BTFVkylu.js
app.C2ONFNRQ.js

Дальше я искал по тексту важные слова. Сначала такие:

rg "Record voice message|MediaRecorder|getUserMedia|AUDIO|audioId|sendChatMessage|cmd\\(64" /tmp/max-web-bundles

Главные находки:

Что искал Что это дало
Record voice message Нашлись строки интерфейса: кнопка записи, “Stop recording”, “Delete recording”. Это подтвердило, что voice UI живет в веб-клиенте.
MediaRecorder, getUserMedia Нашел код записи с микрофона и кодеки: audio/ogg; codecs=opus, AAC/MP4 fallback.
AUDIO, audioId, duration, wave Нашел формат аудио-вложения MAX.
sendChatMessage, cmd(64) Нашел команду реальной отправки сообщения через внутренний WebSocket.

Самое важное место оказалось в CHBUOM21.js. Там была функция сериализации вложений:

case e instanceof WW:
case e instanceof lG:
  return {
    _type: "AUDIO",
    audioId: e.id,
    duration: e.duration,
    wave: e.wave,
    token: e.token ?? void 0
  }

Отсюда стало понятно: чтобы MAX считал сообщение аудио, ему нужен attach типа AUDIO, а не обычный файл.

Как я понял, что mod.ja — нужная функция

После поиска по бандлу стало видно, что некоторые функции экспортируются наружу из модуля. У MAX Web в импортированном бандле были экспортированные имена, в том числе ja. Внутри эта функция вела к коду, который создает аудио-вложение и запускает отправку.

Почему это важно: если функция экспортирована, ее можно вызвать из консоли страницы или из Playwright через await import(bundleUrl). То есть не нужно имитировать удержание кнопки мышью. Можно вызвать тот же внутренний путь, которым пользуется MAX Web.

Какие рабочие файлы получились по дороге

Во время исследования я не писал один идеальный скрипт сразу. Сначала были маленькие проверочные скрипты, каждый отвечал на один вопрос:

Файл Зачем был нужен
inspect_max_storage.js Понять, какие ключи MAX лежат в Local Storage Chrome и есть ли __oneme_auth.

6. Что значит “код обфусцирован”

Обфускация — это когда код специально или автоматически превращается в трудно читаемый вид. Не обязательно для защиты от хакеров; часто это просто результат сборки production-приложения.

Например, вместо красивых имен:

sendChatMessage(chat, message)
AudioAttachment
UploadQueue

в бандле встречается:

dJ
WW
VW
CG
L0r
I0r

То есть имена почти ничего не говорят. Поэтому я искал не “красивое название функции”, а поведение:

  • где встречается строка AUDIO;
  • где вызывается WebSocket-команда cmd(64);
  • где запрашивается upload URL через cmd(82);
  • где есть поля audioId, duration, wave, token.

Это обычный прием чтения минифицированного кода: идти не от имен, а от строк, констант и формы данных.

Как читать такой код, если ты новичок

  1. Не пытаться понять весь файл целиком. Большой бандл может быть на тысячи строк.
  2. Искать уникальные слова: AUDIO, audioId, MediaRecorder, текст кнопок.
  3. Когда нашел слово, читать 20-50 строк вокруг.
  4. Выписать структуру данных: какие поля есть у объекта.
  5. Искать, куда этот объект передается дальше.
  6. Проверять гипотезы в Console или во временной Playwright-сессии.

Например, строка _type: "AUDIO" сама по себе еще не отправляет сообщение. Но она показывает формат, который должен попасть в команду отправки. Следующий вопрос: где этот объект используется? Так поиск приводит к cmd(64).

7. Что я искал в локальной базе Chrome

Чтобы не нажимать кнопки в открытом браузере, нужен был способ открыть временную MAX Web-сессию уже авторизованной. Для этого я посмотрел, где Chrome хранит данные MAX.

Chrome хранит Local Storage сайтов в LevelDB:

~/Library/Application Support/Google/Chrome/Default/Local Storage/leveldb

Я проверил, в каком профиле лежат следы MAX:

python3 - <<'PY'
from pathlib import Path
root = Path.home() / "Library/Application Support/Google/Chrome"
for prof in [p for p in root.iterdir() if p.is_dir() and (p.name == "Default" or p.name.startswith("Profile"))]:
    hits = []
    for sub in ["Local Storage/leveldb", "IndexedDB", "Session Storage"]:
        p = prof / sub
        if not p.exists():
            continue
        for f in p.rglob("*"):
            if f.is_file() and f.stat().st_size < 100_000_000:
                data = f.read_bytes()
                if b"web.max.ru" in data.lower() or b"oneme" in data.lower():
                    hits.append(str(f.relative_to(prof)))
    if hits:
        print("PROFILE", prof.name)
        for h in hits[:20]:
            print(" ", h)
PY

Так стало ясно, что нужная авторизация MAX находится в профиле Default.

Зачем вообще смотреть локальную базу

Обычный пользователь уже вошел в MAX в своем Chrome. Значит, где-то в профиле Chrome есть данные, которые позволяют MAX Web понять: “это авторизованный пользователь”. Чтобы временная автоматизированная сессия тоже открылась авторизованной, надо перенести эти данные в новый временный профиль.

Я не искал “пароль”. Пароля там нет и он не нужен. Я искал именно браузерные данные сессии MAX Web: ключи Local Storage, которые сам сайт использует после входа.

Ключи MAX в Local Storage

Потом я прочитал LevelDB через Node-пакет classic-level и перечислил только безопасные сведения: имена ключей и длины значений, без публикации токенов.

npm install classic-level

Среди ключей был главный:

_https://web.max.ru\0\1__oneme_auth

Внутри него лежит JSON с авторизацией MAX Web. Значение начинается примерно так, но реальные токены печатать нельзя:

{
  "token": "ЗДЕСЬ_СЕКРЕТНЫЙ_LOGIN_TOKEN",
  ...
}

Нельзя публиковать реальный __oneme_auth. Это доступ к аккаунту. В учебном коде его надо читать локально и не выводить в лог.

IndexedDB MAX

Кроме Local Storage, у MAX есть IndexedDB:

~/Library/Application Support/Google/Chrome/Default/IndexedDB/https_web.max.ru_0.indexeddb.leveldb

Там лежит локальный кэш чатов и сообщений. По строкам внутри нашлась база вида:

max-db-14-125622089

Это помогло подтвердить, что веб-клиент MAX кэширует чаты локально, но для отправки сообщения важнее оказался __oneme_auth.

Что именно проверялось в базе

  • Есть ли вообще упоминания web.max.ru в профиле Chrome.
  • В каком профиле Chrome они лежат: Default или другом Profile ....
  • Есть ли ключи, начинающиеся с __oneme.
  • Есть ли среди них __oneme_auth.
  • Есть ли IndexedDB-база MAX, подтверждающая, что сайт хранит локальный кэш.

При этом реальные значения токенов не переносились в HTML и не публиковались. В учебной странице можно показывать имена ключей, но не содержимое секретов.

8. Как устроена отправка аудио внутри MAX

В коде MAX нашлась цепочка:

  1. Создается аудио-attach класса WW.
  2. Он кладется в коллекцию вложений VW.
  3. Создается сообщение CG.
  4. MAX запрашивает upload URL через WebSocket-команду cmd(82).
  5. Файл грузится на выданный URL.
  6. Сообщение отправляется через cmd(64).

Важные фрагменты, которые это показали:

// запрос upload URL для audio/video
send(82, {
  count: 1,
  type: 2,
  uploaderType: ...
})

// отправка сообщения
socket.cmd(64, {
  chatId,
  postId,
  message: {
    text,
    cid,
    elements,
    link,
    attaches: vG(message.attaches)
  },
  notify: true
})

Формат аудио-вложения после сериализации:

{
  _type: "AUDIO",
  audioId: "...",
  duration: 193369,
  wave: Uint8Array(...),
  token: "..."
}

duration — длительность в миллисекундах. wave — массив амплитуд для визуальной волны в аудио-плашке.

Что такое wave и зачем он нужен

В аудиосообщениях обычно показывается “волна” — маленькие вертикальные палочки, похожие на форму звука. MAX хранит эту волну отдельным массивом чисел. Это не само аудио, а визуальная подсказка для интерфейса.

В упрощенном варианте можно создать искусственную волну:

const wave = new Uint8Array(
  Array.from({ length: 80 }, (_, i) => {
    return 28 + Math.round(20 * Math.abs(Math.sin(i / 5)));
  })
);

Для идеального решения волну можно считать из реального аудиосигнала. Но для публикации аудио-плашки MAX достаточно корректного массива.

9. Почему первый “успех” оказался ложным

Сначала я отправлял .ogg Opus. В UI появилась аудио-плашка 03:13, и это выглядело как успех. Но после чистой перезагрузки канала сообщения не было.

Причина нашлась в консоли MAX Web:

[0] cmd errored [0x40 errors.process.attachment.video.not.ready]
Key: errors.process.attachment.video.not.ready

Что это значит простыми словами: клиент MAX нарисовал локальную плашку, но сервер отказался публиковать сообщение, потому что вложение еще не было готово.

В коде MAX видно, почему возник race condition:

// упрощенно:
sendChatMessage(chat, message)   // сообщение уже пытаются отправить
startAudioUpload(attach)         // upload начинается после этого

В обычном UI это компенсируется очередью и состояниями загрузки. При прямом вызове функции из скрипта сообщение могло уйти слишком рано.

Именно поэтому я перестал считать “плашка появилась на экране” успехом. Успех — это когда после новой загрузки страницы сервер возвращает это сообщение обратно.

10. Что в итоге сработало

Сработал вариант через .m4a, а не через .ogg. Для .m4a MAX включает ветку обработки, где сервер успевает подготовить аудио. После этого чистая перезагрузка канала показала реальное аудио-сообщение:

03:13
01:52 PM

То есть итоговая логика была такая:

  1. Из MP4 сделать M4A.
  2. Взять авторизацию MAX Web из локального Chrome Local Storage.
  3. Открыть временный Chrome-профиль.
  4. Записать туда ключи __oneme_... в Local Storage.
  5. Открыть https://web.max.ru/-79157065918537.
  6. Импортировать основной JS-бандл MAX CHBUOM21.js.
  7. Найти объект чата в mod.Co.chats.cache по chat.id === "-79157065918537".
  8. Вызвать экспортированную функцию аудио-отправки mod.ja(...).
  9. Проверить результат в новой чистой сессии.

Ниже путь “как повторить исследование”, а не только готовая команда. Идея в том, чтобы студент понял, почему каждый шаг нужен.

Шаг 0. Открыть канал и убедиться, что ты авторизован

  3. Убедиться, что канал открывается и аккаунт может писать в него.

Шаг 1. Подготовить рабочую папку

Шаг 2. Сделать аудио из MP4

Делаем M4A:

ffmpeg -hide_banner -y \
  -i "/Users/servas/Downloads/_Подмосковные вечера - BENKO DIXIELAND BAND.mp4" \

Здесь -i указывает входной MP4, -vn отключает видео, -c:a aac выбирает аудиокодек AAC, -b:a 128k задает битрейт, а -movflags +faststart делает файл удобнее для быстрого старта проигрывания в вебе.

Шаг 3. Найти авторизацию MAX в Chrome

Нужно прочитать Local Storage Chrome, но не печатать токены. Минимальная идея:

const { ClassicLevel } = require("classic-level");

async function readMaxLocalStorage() {
  const dbPath = `${process.env.HOME}/Library/Application Support/Google/Chrome/Default/Local Storage/leveldb`;
  const db = new ClassicLevel(dbPath, {
    keyEncoding: "utf8",
    valueEncoding: "utf8"
  });

  const out = {};

  for await (const [key, rawValue] of db.iterator()) {
    if (!key.startsWith("_https://web.max.ru\\0\\1__oneme")) continue;
    const localKey = key.split("\\0\\1")[1];
    out[localKey] = rawValue.startsWith("\\1")
      ? rawValue.slice(1)
      : rawValue;
  }

  await db.close();

  if (!out.__oneme_auth) {
    throw new Error("MAX auth was not found");
  }

  return out;
}

12. Безопасность и аккуратность

  • Никогда не выкладывать содержимое __oneme_auth.
  • Не коммитить токены в GitHub.
  • Не логировать полный Local Storage.
  • Не отправлять посты в чужие каналы.
  • После экспериментов проверять канал чистой загрузкой, а не верить локальной плашке в текущем DOM.
  • Если видишь ошибку errors.process.attachment.video.not.ready, значит сервер еще не готов принять attach в сообщение.

Ключевой урок. В веб-приложениях часто есть разница между “UI показал локальный pending” и “сервер реально опубликовал сообщение”. Всегда проверяй результат через новую загрузку страницы или вторую сессию.
